# 批次一：纯前端三件套

## #1 行程导出 .ics 日历（B5，性价比之王）

**目标**：行程结果页一键下载 .ics 文件，双击导入手机/电脑日历，每天的行程变成日历日程。

**现状依赖**：
- 行程 plan JSON 已在前端 store（ResultView 已实现导出攻略 PDF，说明 plan 结构可直接读取）
- 每天站点含 name、日序；日期来自 startDate

**方案**：
1. ResultView 顶栏操作区（🐼 故事卡按钮旁）新增「导出到日历」按钮，三语文案 `ics.*` 键
2. 纯前端生成 .ics（Blob + `URL.createObjectURL` 下载），无需后端：
   - 每个景点生成一个 `VEVENT`：`DTSTART`/`DTEND` 按"第 N 天 = startDate + N-1"，若 plan 有具体时段用之，否则默认 09:00–12:00 / 14:00–18:00 两个半天块
   - `SUMMARY` = 景点名；`DESCRIPTION` = 站点简介（多语按当前界面语言 pickDesc）；`LOCATION` = 景点名（日历 App 会自动关联地图）
   - `TZID=Asia/Shanghai`，`DTSTAMP` 用当前时间；注意 CRLF 换行与 75 字符行折叠（ICS 标准）
   - 文件名：`行程-{城市}-{起始日}.ics`
3. 无具体时段的 day 整体生成一个全天事件（`DTSTART;VALUE=DATE`）

**涉及文件**：`src/trip/views/ResultView.vue`（入口按钮）、新建 `src/trip/utils/ics.ts`（生成器）、三语 locales

**验收**：下载的 .ics 在 Windows 日历/手机导入后出现对应日程；中英文界面导出的描述语言正确

**风险**：极低。ICS 字段兼容性按最小集（SUMMARY/DTSTART/DTEND/LOCATION/DESCRIPTION）保证。

## #2 多币种预算换算（B7，呼应国际传播）

**目标**：行程预算支持 CNY / USD / JPY / EUR 切换，境外用户按界面语言自动选默认币种。

**现状依赖**：plan.budget 已含门票/酒店/餐饮/交通分项与总额（既有字段）。

**方案**：
1. 汇率数据：免费无 Key API `https://open.er-api.com/v6/latest/CNY`，前端 fetch 后缓存 localStorage（TTL 24h，键 `tripstar.fx_rates`）；请求失败或超时回落"仅显示 CNY"
2. 预算展示区加币种切换（a-select 或分段控件）：默认币种按界面语言——zh→CNY、ja→JPY、en→USD
3. 换算只在前端展示层做：`原值 × rate`，汇率 >1 的币种金额取整（USD 保留 2 位可按值大小自适应），下方小字标注"按 1 CNY ≈ 0.14 USD 汇率换算，仅供参考"（三语）
4. 不改任何接口与存储——plan JSON 仍存人民币原值

**涉及文件**：ResultView 预算组件、新建 `src/trip/utils/fx.ts`、三语 locales

**验收**：切换币种金额联动；断网时优雅回落 CNY；刷新页面汇率缓存生效（无重复请求）

**风险**：低。er-api 免费额度足够演示；汇率接口挂掉不影响主流程。

## #3 语音输入问答（B8，ASR 输入闭环）

**目标**：AI 问答输入框加麦克风按钮，按住/点击说话转文字，与 TTS 语音导览形成"语音进、语音出"闭环。

**现状依赖**：AIChat.vue 已有输入框与发送逻辑；TTS（输出）已在景点详情页实现。

**方案**：
1. 使用浏览器原生 `webkitSpeechRecognition`（Chrome/Edge 支持，免费、无需 Key）：
   - `lang` 跟随界面语言：zh-CN / en-US / ja-JP
   - `continuous=false, interimResults=true`，识别中实时显示临时文本
2. 输入框右侧加麦克风按钮（录音中变红/脉冲动效）；识别结果填入输入框（不自动发送，用户确认后发送，避免误识别）
3. 浏览器不支持（Firefox）或非 https/localhost 环境 → 按钮隐藏并 `title` 提示
4. 点击麦克风若未授权麦克风权限，浏览器原生弹窗处理；被拒绝则 message 提示三语文案

**涉及文件**：AIChat.vue、新建 `src/trip/utils/speech-recognition.ts`（能力探测 + 封装）、三语 locales

**验收**：Chrome 下中文语音输入转文字并正常发送问答；语言切换后识别语言跟随；Firefox 下按钮不出现

**风险**：低。Web Speech API 在 Chrome 内核可用性稳定；失败模式全部静默降级。

# 批次二：后端三件套（共享基建，统一回归）

## #4 LLM 行程语义缓存（A3，成本优化技术亮点）

**目标**：相同"城市+天数+核心需求"的行程生成请求命中 Redis 缓存，秒回且不消耗 LLM 额度。答辩可讲"轻量指纹缓存 → embedding 语义缓存"的演进路径。

**现状依赖**：
- Redis 已在栈内：`database/redis.go`（go-redis v9，已用于景点实时数据缓存，config 已有连接配置）
- 行程生成入口在 trip 服务层（LLM 调用 + 异步任务），参数含城市/天数/用户需求/偏好记忆

**方案（轻量指纹缓存，不做 embedding）**：
1. 缓存键：`sha256(city|days|startDate|normalize(需求文本)|model名)`，`normalize` = 去空格/标点/转小写（城市与天数是主要区分维度）
2. 命中策略：生成任务启动时先查 Redis（TTL 24h，键前缀 `trip:plancache:`）
   - 命中 → 任务直接标记完成，plan JSON 从缓存反序列化，日志打 `[行程缓存] 命中`
   - 未命中 → 正常生成，成功后写缓存
3. **旁路规则（必须）**：
   - 偏好记忆开启（memory_enabled=true）时绕过缓存（个性化与缓存冲突，个性化优先）
   - 用户填了自定义特殊要求时进入键计算（不同要求不同键），但要求文本含"小众/冷门/独特"等强个性词时也绕过——宁可多花一次 LLM 也不回千篇一律结果
   - 后台开关 `TRIP_PLAN_CACHE_ENABLE`（.env，默认 true），runtime_settings 可热切
4. 缓存只存后端生成的 plan JSON 本体（不含图片直链），读取后走既有图片代理管线，无失效问题

**涉及文件**：trip 服务层生成入口 + 新建 `service/trip_plan_cache.go`；config 加开关

**验收**：同参数连续生成两次，第二次秒回且后端日志显示命中；开启偏好记忆后不命中；关缓存开关后行为恢复

**风险**：低。最坏情况是缓存污染（生成了不理想的计划被复用）→ TTL 24h 自动过期 + 可一键关闭。

## #5 RAG 库内知识问答（A2，故事引擎价值翻倍）

**目标**：AI 问答能回答"宽窄巷子晚上几点清场""麻婆豆腐有什么典故"这类**库内已有**的知识，且回答明确基于资料而非编造。

**现状依赖**：
- 知识库现成：scenic_spots（23 条，desc/desc_en/desc_ja/culture_note）+ foods（23 条，同结构多语字段）
- chat 入口在 service/trip_chat.go（已有 plan 上下文注入，现改为"plan + 检索资料"双上下文）

**方案（MySQL ngram 全文检索，不引入向量库）**：
1. 建索引：`ALTER TABLE scenic_spots/foods ADD FULLTEXT INDEX ft_rag(name, desc, desc_en, desc_ja, culture_note_*) WITH PARSER ngram`（MySQL 内置 ngram 分词器天然支持中文，2-gram；迁移脚本带中文 comment 与存在性判断，重复执行安全）
2. 检索流程（chat 请求进来时）：
   - 取用户问题 → 提取关键词（先简单处理：按空格/标点切分 + 去停用词；短句直接整句检索）
   - `MATCH...AGAINST` 查两张表，按相关度取 **top 3** 片段（每条截取 500 字符，含 name 与匹配语言列）
   - 按当前界面语言选列：en→desc_en 优先回落 desc；ja 同理
3. Prompt 注入：system prompt 加一段"以下是站内资料摘录，回答涉及相关内容时必须且只能依据资料；资料中没有的信息明确告知不确定，禁止编造"，资料块用分隔符包裹
4. 检索失败/无命中 → 完全回退现有行为（只有 plan 上下文），对用户透明
5. 日志：`[RAG] 命中 n 条资料 (query=...)` 便于调参

**涉及文件**：`service/trip_chat.go`（注入逻辑）、新迁移 SQL 或 AutoMigrate 后补 FULLTEXT（GORM 不支持 FULLTEXT，需要 raw SQL migration）、database 初始化处执行

**验收**：问"麻婆豆腐的典故"回答引用库内文化注解内容；问库内没有的（如"九寨沟门票"）回答"不确定"而非编造；三语界面下检索对应语种列

**风险**：低-中。ngram 索引在 MySQL 5.7+ 可用（本机 MySQL 版本需确认，若是 5.6 降级为 LIKE 多关键词 OR 检索，23 条数据 LIKE 完全够用——**优先直接用 LIKE 方案保底，FULLTEXT 作为优化项**）。

## #6 行程合理性体检（A1，行业级工程创新点）⭐ 批次二核心

**目标**：解决 LLM 行程产品通病——地理上不合理的排布（如"上午宽窄巷子、中午都江堰、下午回锦里"）。生成后自动检测、自动重排，给用户"体检通过 ✓"的确定感。

**现状依赖**：
- AMap 客户端已有（地理编码/路线规划/距离能力，trip 服务层）
- plan JSON 已含每天站点顺序与坐标（AMap POI 检索/地理编码已产出）
- LLM 调用管线已有（含 JSON 提取与重试加固 extractJSONObject）

**方案**：
1. 新建 `service/trip_health.go`，生成任务在 LLM 出稿后、落库前执行：
   - **逐日检查**：对每天站点序列取相邻两点调 AMap 驾车路线规划（已有能力，返回距离+耗时）
   - **规则判定**：单段距离 >40km（同城场景）或驾车 >90 分钟 → 记为 issue：`{day, from, to, distance_km, duration_min, severity}`
   - 多日多城行程（如都江堰-青城山日）阈值放宽到 60km，避免误报——阈值常量可配置
2. **自动修复**：存在 issue 时，把 issue 列表作为约束发一次 LLM 重排请求（"以下站点存在距离冲突，请调整同一天内的顺序或分组，只输出重排后的 JSON"），复用既有 LLM JSON 管线；重排后**复检一次**，仍有 issue 则保留原稿并如实标注（最多修复一轮，避免死循环）
3. **结果落库**：plan JSON 新增 `health_report` 字段：`{checked: true, issues: [...], fixed: true/false, fixed_at}`（只增字段，旧计划无此字段前端兼容处理）
4. **前端展示**：ResultView 顶部状态条——通过：「✓ 行程体检通过，路线顺路合理」；已修复：「已自动调整 x 处绕路安排」；未修复：「发现 x 处较长交通段，建议按提示调整」（琥珀色提示，可展开看明细），三语文案
5. **开关与降级**：`TRIP_PLAN_HEALTH_ENABLE` 默认开；AMap 调用失败或超时（3s/点）→ 跳过体检照常出稿（体检绝不能阻塞主流程）；历史计划点开时不补检

**涉及文件**：新建 `service/trip_health.go`；行程生成服务接入；model/trip.go 的 plan 结构加可选字段；ResultView 状态条 + 三语 locales

**验收**：构造跨城日（手动提需求"成都市区+都江堰+回市区一天"）触发改写；正常行程显示体检通过；AMap 断网时计划正常生成（体检静默跳过）

**风险**：中低。最大风险是 LLM 重排改坏 JSON → 已有 extractJSONObject + 解析重试兜底，且失败保留原稿，最坏退化为"只检测不修复"。

# 批次三：大件

## #7 拍照识景点（A4，多模态，先探测再实施）

**目标**：用户在景点拍照上传，AI 识别并讲故事（结合库内 RAG 资料回答"这是哪/有什么故事"）。

**⚠️ 前置探测（实施前必须，半天内完成）**：
- 用 runtime_settings 当前配置的模型发一条带图片的 OpenAI 兼容消息（`content: [{type:"text"},{type:"image_url"}]`），确认模型支持 vision
- **支持 → 继续；不支持 → 本项直接取消或降级为"文字描述识别"（用户口头描述所见，走 RAG 匹配），不做无意义封装**

**方案（假设模型支持）**：
1. 前端：AIChat 输入框加图片按钮，支持相册选择（不做拍照 API，file input `accept="image/*"` 手机端自动唤起相机）；前端压缩到最长边 1280px + JPEG 0.8（Canvas 压缩，控制 base64 <1MB）
2. 后端：chat 请求体新增可选 `image` 字段（base64 或已上传 URL）；有图时消息构造为 vision 兼容格式；prompt 要求"识别图中建筑/食物/场景，若与站内景点匹配则引用库内资料讲解（接 #5 RAG），不匹配则如实说明"
3. 图片存储：临时场景直接 base64 透传 LLM（不落 OSS，日志里也不记录图片内容，规避隐私风险）
4. 与 #5 协同：识别结果若命中库内景点，返回景点 id，前端显示"查看详情"链接跳转

**涉及文件**：trip_chat 服务（消息构造）、AIChat.vue（上传 UI）、api.ts

**验收**：上传武侯祠照片 → 识别并引用库内资料讲三国故事；上传无关照片 → 如实说明；上传超大图自动压缩成功

**风险**：**中**。全部押注在模型 vision 能力上（前置探测规避）；若模型对 image_url base64 格式有兼容问题（部分国产模型要求 URL），需改走 OSS 上传中转，工作量 +0.5 天。

## #8 管理后台（B6，行业交付硬门槛，工作量最大）

- JWT 中间件已有（需确认 users 表是否已有 role/is_admin 字段，没有则加 `is_admin TINYINT(1)`，中文 comment）

**方案**：
1. **权限**：users 加 is_admin；登录响应带出；后端新路由组 `/api/admin/*` 挂 JWT + admin 中间件双重校验 + 更严格限流
2. **后台页面**（前端 `/admin` 路由，非 admin 访问重定向）：
   - **内容管理**：景点/美食/路线三个列表页（分页+搜索+多语字段编辑表单；编辑保存走 UpdateFields 扩展的 admin 接口；图片字段可直接贴 OSS 地址）
   - **日志查询**：log_entries 按模块/级别/时间筛选 + 分页（复用 logger 表结构，只加查询接口）
   - **运营概览**：用户数 / 行程生成数（trip_plans count）/ 近 7 日请求趋势（log_entries group by date）——三个数字卡 + 一张简单趋势表（不引图表库，CSS 柱状即可）
3. **接口清单**（全部只增）：
   - `GET/PATCH /api/admin/scenics/:id`、`GET/PATCH /api/admin/foods/:id`、`GET/PATCH /api/admin/routes/:id`
   - `GET /api/admin/logs?module=&level=&page=`
   - `GET /api/admin/stats/overview`
4. **样式**：后台用现有 ant-design-vue 组件库直接拼，不做视觉定制（后台不求美观求可用）

**涉及文件**：后端新建 `handler/admin_handler.go` + `router` admin 组 + `middleware` admin 校验；前端新建 `src/admin/`（Layout + 4 页面）+ 路由守卫

**验收**：admin 账号登录可改景点英文名并前台即时生效；非 admin 账号请求 admin 接口 403；日志筛选与统计数字与 DB 实际一致

**风险**：中。工作量最大且涉及权限，放最后、可整体砍掉不影响其他项；users 表加字段走既有 AutoMigrate，风险可控。**若比赛时间紧，做"内容管理 + 运营概览"两块即可，日志查询可裁剪。**

## #9 主题文化路线（0.5 天）

**传播点**：现有 4 条路线是"玩法逻辑"（亲子/深度），缺"文化逻辑"——把武侯祠、锦里、草堂、金沙按主题串成故事线，才是"讲好蜀文化"的直接载体。

**落地**：
1. routes 表直接新增数据行（复用现有全部多语字段），首批 3 条：**三国寻踪**（武侯祠→锦里→万里桥遗存）、**诗歌之路**（杜甫草堂→浣花溪→望江楼·薛涛）、**古蜀探源**（金沙遗址→三星堆（周末特别线）→博物馆）
2. description/description_en/ja 由 LLM 以"文化叙事"口吻改写（一条路线一个故事钩子，如"跟随杜甫的足迹，从一座茅屋读懂成都的温柔"）
3. routes 表加 `theme` 字段（varchar，中文 comment，存 `culture` 或空）——routes 页加"文化主题"筛选标签；不改动既有路线数据
4. 首页"探索"区块给文化路线一个入口位

**涉及**：SQL 数据 + description 多语批量生成（story-enrich 加 `-kind route-theme` 或直接 SQL 手工+LLM 生成后入库）、RoutesPage 筛选 UI、三语 locales

**验收**：三语界面下文化路线列表与详情完整；旧路线不受影响

## #10 历史人物 AI 对话（0.5 天）⭐ 传播爆点

**传播点**：杜甫、诸葛亮是国际认知度最高的蜀文化 IP（杜甫入选联合国教科文组织"世界文化名人"）。**"和诗圣本人聊聊他在成都的日子"**——这是答辩演示里最容易被记住的一幕。

**落地**：
1. 纯 prompt 工程复用现有 chat 管线：新建 `service/persona_chat.go`，预置 persona 配置（杜甫/诸葛亮各一份）：
   - 人设约束：第一人称、基于库内景点资料与公认史实、语言符合人设气质（杜甫沉郁温厚/诸葛亮持重睿智）、三语跟随界面语言
   - 资料注入：复用 #5 RAG 的检索结果（杜甫相关景点 desc/culture_note 直接成为"他自己的记忆"）——**#10 与 #5 强协同，建议排在 RAG 之后实施**
2. AIChat 页顶部加"对话角色"切换（默认普通助手 / 杜甫 / 诸葛亮），角色头像用现有 Canvas 手绘风（故事卡熊猫脸管线同款画法）
3. 安全约束写入 prompt：不讨论敏感话题、不冒充真人、被问到超出时代的问题（如手机）用人设内巧妙回应（"此物老夫未曾见过，敢问是何方神物？"）——这本身就是传播梗
4. 新接口 `POST /api/trip/persona-chat`（入参 persona_id + messages），与普通 chat 隔离，便于独立限流

**涉及**：新建 persona_chat 服务 + handler + 路由、AIChat.vue 角色切换 UI、三语 locales（角色介绍文案）

**验收**：英文界面用英语与"Du Fu"对话，他能引用草堂资料谈《茅屋为秋风所破歌》的创作心境；问现代话题回答保持人设

## #11 每日蜀签（1 天）

**传播点**：像"每日英语听力"一样，每天一条蜀文化知识签（一句诗 / 一个方言词 / 一条冷知识），**日更内容给用户回来的理由**，卡片设计成可截图分享的规格。

**落地**：
1. 新表 `culture_daily`（id / content_zh / content_en / content_ja / category(诗句/方言/冷知识) / related_spot_id 可空 / display_date 唯一索引，全字段中文 comment）
2. 内容生成：仿 story-enrich 新建 `cmd/daily-gen`，一次批生成 60 条（约两个月的量），LLM 基于库内景点/美食资料出题，落库
3. 展示：首页顶部落地区块下加"今日蜀签"卡——按 `display_date = CURDATE()` 取当日（无则取最新一条兜底），三语跟随界面语言，含"换一条"按钮（随机未看过的）
4. 分享：卡片右下角复用 qrcode 管线生成站点码，长按/右键存图（不另做 Canvas，保持轻量；若要 Canvas 化与 #14 合并做）
5. related_spot_id 非空时卡片下挂"去看看 →"跳景点详情——**日签变成内容分发入口**

**涉及**：新 model/repo/cmd、首页卡片组件、三语 locales

**验收**：当天日期取到对应签；切换语言内容切换；连续两天访问内容不同

## #12 诗词地图（1 天）⭐ 文化深度最高

**传播点**："窗含西岭千秋雪，门泊东吴万里船"——杜甫在成都写的诗至今能对上地名。**景点 × 诗词绑定后，用户站在草堂读到的不是导游词，是 1200 年前的原句**（附英/日译）。

**落地**：
1. 新表 `poems`（id / title / dynasty / author / content_zh / content_en / content_ja / plain_zh 白话赏析 / related_spot_id，中文 comment）
2. 数据：首批 15-20 首与库内 23 景点强相关的经典诗（杜甫草堂系、望江楼薛涛系、武侯祠《蜀相》系），原文人工核对（**原文用权威文本录入，只让 LLM 做三语翻译和白话赏析——诗词原文绝不能让 LLM 生成，防止改字**）
3. scenic_spots 详情页加"相关诗词"卡（无关联则不显示）：原文竖排或大字排版 + 作者朝代 + 可展开的三语译文与白话赏析；语音导览（已实现）支持朗读诗词三语版
4. trips 无关，纯内容层——不动任何行程接口

**涉及**：新 model/repo（人工录入 SQL）、ScenicDetail 诗词卡、三语 locales、（可选）storyI18n 不适用因原文必须显示中文+译文并列

**验收**：草堂详情页显示《春夜喜雨》全文 + 展开英译；语音朗读正常；无关联景点页面无空卡片

## #13 节气 × 蜀俗（1 天）

**传播点**：二十四节气是联合国非遗，蜀地节气习俗（冬至羊肉汤、立夏吃蛋、谷雨采茶）是"活着的蜀文化"。**网站随节气自动换内容**——评委每次打开日期不同，看到的内容也不同，这是天然的"常看常新"。

**落地**：
1. foods 表加 `solar_terms` 字段（varchar，中文 comment，存逗号分隔节气名，如 `冬至`）——现有 food-enrich 管线加一轮批量打标（LLM 按食材/习俗判断，置信低的留空）
2. 节气计算：纯算法（通用节气近似日期表或 API），新建 `src/utils/solar-term.ts`，无后端依赖
3. 首页按当前节气（容差 ±3 天）展示"节气蜀俗"条幅：文案三语（LLM 预生成 24 条模板存 locales 或 culture_daily 表 category=节气）+ 推荐对应打标美食（如冬至推羊肉汤）
4. 无匹配节气内容时静默不显示，页面与现在一致

**涉及**：foods 字段 + 一轮批量打标、solar-term 工具、首页条幅组件、三语 locales

**验收**：改动系统时间测试不同节气展示；冬至时首页出现羊肉汤推荐；无节气数据时页面无空块

## #14 川剧脸谱分享海报（1 天）

**传播点**：川剧变脸是海外认知度最高的中国表演艺术之一。故事卡海报（Canvas 1080×1440 管线现成）加**脸谱模板**——用户行程/护照生成一张"变脸"风格分享图，视觉冲击力远超文字。

**落地**：
1. StoryCardModal 加模板切换：熊猫模板（现有）/ 脸谱模板
2. 脸谱绘制：Canvas 对称几何画法（复用熊猫脸 drawPandaFace 的对称循环技巧）——红/蓝/金三色简化脸谱 + 两侧对称纹样；难度集中在一次函数，失败可退化为"脸谱角标"（海报角落放小脸谱，主体沿用现有排版）
3. 文案骨架沿用现有 story API（标题+正文），仅换视觉模板；二维码管线直接复用
4. 护照证书（PassportPage）同样加脸谱模板选项——两处共用一个新 `drawMaskPoster` 函数

**涉及**：StoryCardModal.vue / PassportPage.vue 模板切换、新建 canvas 脸谱绘制模块、三语 locales

**验收**：两种模板切换渲染正常、可下载；脸谱图案对称无错位；低性能设备生成时间 <2s

## #15 蜀文化知识闯关（1.5 天）⭐ 接护照做留存闭环

**传播点**：护照集章（已实现）解决"来过"，闯关答题解决"看懂"——**集章 + 答题 + 徽章三层游戏化**，把被动浏览变成主动学习，国际用户用英文答关于成都的题，本身就是传播行为。

**落地**：

2. 题目生成：仿 story-enrich 新建 `cmd/quiz-gen`，LLM **严格基于库内 desc/culture_note 出题**（选择题×3 选项，附解析，解析引用库内原文——保证答案可溯源），每景点 2 题，批生成约 46 题

   - 护照页（/passport）已集章的景点格 → "答一题得徽章"角标
